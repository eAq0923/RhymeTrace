# “韵”项目阶段性共识

> 更新时间：2026-09-21  
> 状态：讨论阶段，本文记录当前共识，不代表最终论文方案。

## 1. 项目定位

“韵”是一个大学生大创项目，拟将古典音韵研究与一个小而精的 Web 产品结合起来。

当前更准确的产品定位是：

> 用户输入一个可能作为韵脚的汉字，系统展示它的韵部归属、相关诗歌证据，以及基于已核验语料得到的用韵观察。

网站是研究成果的展示和探索入口，不替代语料整理、韵脚判定和统计分析。

## 2. 研究对象与术语

- “三江”和“四支”是传统平水韵体系中的两个韵部，不是全部韵部，也不是对所有韵脚的完整分类。

- 原方案把“四支”作为相对常用、字数较多的宽韵案例，把“三江”作为相对受限的险韵案例，形成对照样本。

- 目前建议将研究表述收紧为：
  
  > 以四支与三江为案例，探索常用宽韵与典型险韵在古诗中的使用差异。

- 不应宣称仅凭同韵部就能证明诗人具有相似的人生经历。诗体、时代、题材、语言习惯和格律要求都可能造成混杂。

- “诗句末尾字”不等于“韵脚”。不同诗体的押韵位置不同，必须根据诗体规则和人工核验判断。

- 《佩文韵府》是后世韵书体系。项目若使用它统一归类，应明确这是统一标注框架，不直接等同于每个历史时期的实际音系。

## 3. 第一版输入层

为了保持小而美，普通用户的核心输入暂定为：

- 一个汉字，例如“江”“诗”“离”；
- 输入联想和少量示例字可以作为辅助，但不是独立研究功能。

普通用户不需要：

- 自己判断某字是否为韵脚；
- 输入完整古诗；
- 先理解“三江”“四支”等术语；
- 在首屏选择朝代、诗人、体裁等复杂条件。

系统应把用户输入理解为“待查询的字”，而不是用户已经完成的音韵学判断。

需要考虑的技术问题：

- 简体/繁体归一化，例如“诗”与“詩”；
- 多音、多韵或存在歧义的字；
- 无法确认的字不能伪装成唯一归属。

## 4. 第一版输出层

查询结果页暂定只包含四个核心模块：

1. **韵部识别**：输入字、韵部名称、是否属于项目重点样本。
2. **韵部解释**：三江/四支的通俗说明、同韵常见字和必要的术语解释。
3. **诗歌证据**：相关诗句或诗作、题目、作者、朝代和来源；优先展示已人工核验的结果。
4. **研究观察**：由固定统计结果和人工审核说明组成，区分“数据事实”和“可能解释”。

统计结果可包括收录诗作数、作者数、时代分布和高频韵脚字，但第一版不追求完整的诗人画像或全量知识图谱。

## 5. AI 的角色

核心研究观察不由 AI 自由生成。研究结论必须可以复算、追溯和人工审核。

推荐流程：

```text
结构化语料
  -> 固定规则统计
  -> 可复算的数据结果
  -> 研究者撰写/审核观察
```

未来如果接入 AI，只能作为辅助层，例如：

- 将已审核的数据和资料改写成通俗说明；
- 根据受约束的资料回答术语问题；
- 生成供研究者审核的摘要。

AI 不应在缺少证据时自行推断诗人的创作动机，也不能替代韵脚标注和出处核验。第一版可以完全不接 AI。

## 6. 数据库方案

数据库是项目的核心。第一版不建设覆盖所有朝代、所有韵部的庞大数据库，而建设一个可追溯的小型专题语料库。

建议的核心数据实体：

| 数据实体 | 主要内容                      |
| ---- | ------------------------- |
| 韵部   | 韵部名称、平仄/声部信息、说明、来源        |
| 韵脚字  | 原字、规范检索字、韵部、小韵、来源、核验状态    |
| 诗人   | 姓名、朝代、生卒或简介、来源            |
| 诗歌   | 题目、作者、原文、体裁（若能可靠取得）、来源 ID |
| 用韵标注 | 诗歌、句号、韵脚字、韵部、标注方式、人工核验状态  |

最关键的不是简单扫描每一行末字，而是记录：

> 哪首诗的哪一句，以哪个字作为韵脚，被归入哪个韵部，依据是什么。

每条用韵记录应尽量保留来源、核验状态和疑难备注。

## 7. 已有数据源的角色

### 7.1 `chinese-poetry`

本地仓库：

`Database/chinese-poetry-master/chinese-poetry-master`

它可以作为主诗歌语料来源，尤其是 `全唐诗`：

- 单首诗已有 `id`、`title`、`author`、`paragraphs` 等字段；
- 有作者资料文件，例如 `全唐诗/authors.tang.json`；
- 仓库包含 MIT 许可证，但实际发布时仍需保留版权和许可证说明；
- 文本主要为繁体字；
- 该库没有直接提供三江/四支的平水韵归属，也没有可靠的逐句韵脚标注；
- `rank` 目录和重复文集不能直接与全唐诗合并统计，以免重复计数。

因此它提供的是“诗歌原文、题目、作者”的基础数据，不是完整的音韵研究数据库。

### 7.2 `cnpoems`

本地仓库：

`Database/cnpoems-master/cnpoems-master`（仅参考）

它包含声韵参考材料和十三辙诗句集，但不具备结构化的三江/四支字表、逐首诗的作者/体裁/韵脚标注，因此不适合直接作为主数据库。

可以把它作为术语和背景参考，但不能把“十三辙”与平水韵“三江/四支”直接混用。

### 7.3 《佩文韵府》校对手册

本地文件：

`Database/佩文韵府校对手册.pdf`

它不是现成数据库，而是《佩文韵府》数字化校对项目的规范。它确认了《佩文韵府》的层级：

```text
平上去入四声 -> 106卷 -> 韵目 -> 小韵 -> 字头/引文
```

它对本项目的价值是：

- 帮助确定从《佩文韵府》抽取三江、四支字头的方法；
- 规定异体字、疑难字、OCR 错误和修改痕迹的处理方式；
- 提醒我们区分原始字形、规范检索字和人工校勘结论。

它不能直接当作已经整理好的“字 -> 韵部”接口。

## 8. 当前暂定范围

第一版建议暂定为：

- 诗歌范围：优先唐诗，暂不承诺全时代；
- 研究韵部：三江、四支；
- 用户入口：输入一个汉字；
- 核心结果：韵部归属 + 诗歌证据 + 少量可复算统计；
- 数据质量：候选结果自动筛选，最终韵脚由人工核验；
- AI：第一版不作为研究结论引擎；
- 网站：以研究成果展示和单字探索为主，不做大而全的诗词百科。

“唐代近体诗”曾被提出作为更严格的最小样本，但是否采用，要等确认语料中的体裁字段和人工标注成本后再决定。

## 9. 待确认事项

1. 能否从学长处获得“三江”和“四支”已校对的字头清单或对应文本。
2. 这些校对成果能否用于大创项目和网站展示，需确认授权与署名要求。
3. 两个韵部的正式字表如何处理异体字、多音字和小韵层级。
4. 第一版到底选择“全部唐诗候选集”，还是进一步限定为唐代近体诗。
5. 诗体识别和韵脚人工核验由谁负责、采用什么记录格式。
6. 统计时采用“诗作数”“韵脚次数”还是“作者覆盖数”作为主要指标。

## 10. 下一步工作顺序

在《佩文韵府》文本到手前，可以先做：

1. 固定数据库字段和标注格式；
2. 从 `chinese-poetry` 选取 10--20 首唐诗做人工小样本；
3. 记录每句句末字，并明确哪些句子实际押韵；
4. 设计简繁归一化、疑难字和人工核验状态；
5. 用小样本验证“输入一个字 -> 返回诗歌证据”的产品链路。

待《佩文韵府》相关文本到手后，再抽取并核验三江、四支字表，不提前假设其具体字段或字数。
