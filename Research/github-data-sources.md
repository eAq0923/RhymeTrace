## 结论

本次运行环境无法连接 GitHub：对 `https://api.github.com` 的访问被网络策略拒绝。因此，以下 GitHub 条目只能作为**待人工复核的候选来源**，而不是已验证、可直接导入的正式数据源。正式采用前，须在仓库网页或本地克隆副本中逐项查看 README、`LICENSE`、实际字段和数据来源。

本地已有的 `Database/cnpoems-master（参考用）/cnpoems-master` 也**不适合作为正式语料或韵部映射**：其 README 明确同时介绍平水韵、近代韵书和十三辙，实际文件以“十三辙诗句集”和启蒙读物为主，未见结构化的诗题、作者、朝代、正文、韵脚标注数据，也未见许可证文件。

## 最优先核验候选

### 1. `chinese-poetry/chinese-poetry`

- 仓库：<https://github.com/chinese-poetry/chinese-poetry>
- 全唐诗目录（待远程复核）：<https://github.com/chinese-poetry/chinese-poetry/tree/master/%E5%85%A8%E5%94%90%E8%AF%97>
- JSON 样例（待远程复核）：<https://raw.githubusercontent.com/chinese-poetry/chinese-poetry/master/%E5%85%A8%E5%94%90%E8%AF%97/poet.tang.0.json>
- 许可证（采用前必须核验）：<https://github.com/chinese-poetry/chinese-poetry/blob/master/LICENSE>
- 应核验文件：`README.md`、`LICENSE`、`全唐诗/poet.tang.*.json`、作者数据及其他朝代目录。
- 已知用途（待远程复核）：该仓库通常被用作古诗词 JSON 语料候选；应重点检查每条记录是否至少有 `title`、`author` 和 `paragraphs`，以及是否需要由“全唐诗”目录补充“唐代”等朝代字段。
- 适用判断：若许可证允许再分发、JSON 字段完整，可作为“唐诗文本 + 标题 + 作者”的**原始诗歌语料**。它通常不替代韵脚人工校验，且体裁、精确写作年、韵部字段仍需项目自行补建。

### 2. 平水韵 / 《佩文韵府》字表仓库

- 搜索入口：<https://github.com/search?q=%E5%B9%B3%E6%B0%B4%E9%9F%B5&type=repositories>
- 搜索关键词：`平水韵`、`pingshui rhyme`、`佩文韵府`、`三江 四支`。
- 正式纳入的最低标准：
  1. 能逐字导出“字 -> 韵部”的数据，而不只是网页或说明文字；
  2. 明确区分平水韵/《佩文韵府》与十三辙、中华新韵；
  3. 许可证允许项目使用与展示；
  4. 至少抽查“三江”“四支”的字表与纸本韵书或可信数字文本一致；
  5. 记录字的异读、重出或跨韵情况，不能假设一个汉字永远只对应一个韵部。

## 推荐的数据组合

不要试图寻找一个同时满足“权威平水韵映射、完整古诗文本、作者生平、韵脚标注、开放许可证”的单一仓库。更可控的做法是拆分来源：

| 需求 | 推荐来源类型 | 项目中保存的字段 |
| --- | --- | --- |
| 诗歌文本 | 经许可证核验的结构化古诗 JSON 仓库 | 题目、作者、正文、朝代、源仓库与版本 |
| 韵部字典 | 经人工抽查的平水韵/佩文韵府数字字表 | 字、韵部、读音/歧义说明、文献出处 |
| 韵脚 | 项目自己的规则初筛 + 人工复核 | 诗 ID、句号、韵脚字、韵部、核验状态 |
| 诗人背景 | 单独可追溯的权威资料 | 诗人 ID、字段、资料来源、引用位置 |

这样网页的每个统计结果都可回溯到“哪首诗的哪一句、哪个韵脚、哪个分类依据”，不会把现代“江阳辙”误当作平水韵“上平三江”。

## 采用前核验清单

1. 固定仓库 commit SHA 或 release，不只记录分支名。
2. 把原始 README、许可证 URL 和访问日期写进 `source_registry`。
3. 检查 JSON 是否为有效 UTF-8、字段是否稳定、是否有重复诗和空文本。
4. 抽样核对 20 首诗的题目、作者、正文与可靠文本来源。
5. 对“三江”“四支”各抽样 30 个字复核；不确定的字进入 `ambiguous` 队列，不进入自动归类。
6. 发布时注明语料覆盖范围及版本，避免将样本统计表述为全部古典诗歌的结论。
